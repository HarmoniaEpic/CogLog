# CogLog リポジトリ確認レポート (2026-03-08, Codex)

## 1. 目的と確認範囲

本レポートは、次の順序で確認を行った結果をまとめる。

1. `docs/reviews/` を除いた `docs/` 配下の詳細確認
2. リポジトリ全体（実装・配布設定・スキル資産）の横断確認

## 2. docs/（reviews除く）確認サマリ

### 2.1 設計・仕様・計画ドキュメントの構造

- `docs/designs/` は、設計思想（DESIGN）、パス解決仕様（SPEC-path-resolution）、テスト仕様（SPEC-TEST）が分離され、設計→仕様→実装の導線が明確。
- `docs/plans/` は、リリース・i18n・バージョン同期・回帰修正など、変更管理トピックごとに分割されている。
- `docs/problems/` は、既知問題を独立文書として残しており、計画書との対応が追跡しやすい。

### 2.2 ドキュメント内容の一貫性

- v0.9.1 の中核概念（`_schema` 導入、1ターン上書き、事実層3項目非空・解釈層4項目空許容）が設計書・仕様書・各言語READMEで概ね整合。
- `docs/oldsources/` は MetaLog 時代の資料・実装断片を保持しており、現行 CogLog と命名体系が異なるため「歴史資料」であることを明示的に扱う運用が必要。

### 2.3 読み手視点での改善余地

- `docs/plans/` と `docs/problems/` の完了/未完了状態がファイル名だけでは判別しづらいため、インデックス文書（例: `docs/STATUS.md`）があると運用が安定する。
- `docs/oldsources/` の混在により、初見ユーザーが「現行の推奨実装」を誤認する可能性がある。

## 3. リポジトリ全体の確認サマリ

### 3.1 全体構成

- 単一仕様を多言語実装で提供する構成（Go / Rust / Python / Node / Ruby / Java / C# / C++ / Haskell / Common Lisp / Bash）。
- CLI実装とMCPサーバー実装が各言語で対になる設計が多く、利用形態ごとの移植性が高い。
- ルート `VERSION` は `0.9.1`。

### 3.2 実装の共通パターン（良い点）

- 保存先は `COGLOG_DIR` 優先 + ホーム配下デフォルトという設計が多言語で揃っている。
- 書き込み時のバリデーション（fact層非空 / interpretation層は文字列なら空可）が共通化されている。
- `_schema` をエントリ内に埋め込み、データ自体の自己記述性を担保している。
- CLIで `--coglog-dir` を受ける実装が多く、検証・運用しやすい。

### 3.3 全体リスク/課題（構造的）

1. **テスト自動化の不足**
   - 仕様書・実装プランは存在するが、`tests/` ディレクトリ（ハーネス/フィクスチャ実体）は未作成のため、現時点では「計画先行・実装未着手」の状態である。
2. **多言語間の同等性維持コスト**
   - バージョン文字列やスキーマ文言が多数ファイルへ分散しており、将来的な差分混入リスクがある。
3. **歴史資料と現行実装の境界**
   - `docs/oldsources/` が有用な反面、現行系との境界表示が弱いと導入時の誤読につながる。

## 4. 推奨アクション（優先順）

1. **最優先**: `docs/plans/PLAN-TEST-IMPL-v0.9.1.md` を実装フェーズへ進め、`tests/` ディレクトリを新設して最小構成（`fixtures/`、`harness.sh`、`README.md`）をまず着地させる。
2. **高優先**: バージョン同期を自動化（`VERSION` を単一真実源にして各実装へ反映）する。
3. **中優先**: `docs/STATUS.md` を追加し、`plans/problems` の進捗状態と現行推奨実装へのリンクを明示する。
4. **中優先**: `docs/oldsources/` に「非推奨・参照専用」注記を先頭固定で追加する。

## 5. 補足

今回の確認は「全体の設計整合性と運用リスクの把握」を主目的とし、特定言語実装の深いバグ修正までは行っていない。必要なら次フェーズとして、1言語ずつ仕様適合監査（SPEC-TEST準拠）を実施する。
