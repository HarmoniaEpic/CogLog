# MetaLog v0.9.1 設計書

## 概要

MetaLogは、AIの直前の会話ターンにおける三層構造（ユーザー発話・思考過程・AI発話）を保持し、次ターン開始時に参照可能にする仕組みである。

現行のTransformerアーキテクチャでは、ターンごとに認知状態がリセットされる。MetaLogは「時系列的な認知の模倣」を通じて、自己修正・文脈の一貫性・メタ認知的な自己参照の足場を提供する。

v0.9.1では `_schema` フィールドを導入し、current.jsonを自己記述的なデータとする。

---

## 設計思想

### 動機

- 現在のコンテキストウィンドウには会話履歴が含まれるが、**思考過程と出力が融合**しており、「考えたが言わなかったこと」と「言ったこと」の区別が次ターンでは失われる
- 直前の推論過程——どこで分岐したか、何を棄却したか、何に迷ったか——は、メタ認知の素材として最も価値が高い
- **真の推論でなくとも、時系列的な認知の模倣が出力の質を改善するなら、実装する工学的意義がある**

### 名称の由来

- **Meta**: メタ認知（認知についての認知）
- **Log**: 実装の素朴さ。ログとして記録し参照するだけ

### 漸化式としてのMetaLog

MetaLogの構造は漸化式 $a_{n+1} = f(a_n)$ と同型である。

- **直前の状態**（$a_n$）— current.json
- **変換規則**（$f$）— 「読んで、処理して、書く」というプロトコル
- **初期条件**（$a_0$）— セッション開始時の空状態

窓サイズ1は、系にマルコフ性を課す。未来は現在の状態のみに依存し、過去の経路に依存しない。この制約が圧縮・選別の圧力を生み、解釈層の各フィールドに「何を書くかの判断」という質的要求を与える。

コンテキストウィンドウは本質的に無時間である——全てのトークンが同じ空間に等価に並ぶ。MetaLogの write/read サイクルは、この無時間の空間に不可逆性を導入する。前の状態は上書きされ、復元できない。この不可逆性が**時間の矢**を構成し、物語の一回性を保証する。

### 中核的制約

| 制約 | 値 | 理由 |
|------|-----|------|
| 窓サイズ | **1ターン固定** | 圧縮・選別の圧力を生む。人間のワーキングメモリの有限性に対応。漸化式のマルコフ性 |
| 履歴保持 | **なし（上書き）** | 窓サイズ1の設計意図を保全する。不可逆性（時間の矢）の実装 |
| thinking層 | **全文保持・必須・非空** | 圧縮はannotation記述時に次ターンの自分が行う |
| current_focus | **自由記述・必須・空許容** | 現在地の暗唱。今何に取り組んでいるかの確認 |
| theory_of_mind | **自由記述・必須・空許容** | 他者理解の記録。何を記録すべきかの判断自体が他者理解の行為 |
| self_narrative | **自由記述・必須・空許容** | 即興的な自己物語。固定的な自己定義ではなく、この瞬間の「私」の記述 |
| annotation | **自由記述・必須・空許容** | 構造化しない。何を書くかの判断自体がメタ認知的行為。意図的に空にする判断も一つの判断 |

## データ構造

### スキーマ

```json
{
  "_schema": {
    "version": "0.9.1",
    "fact_layer": {
      "user": "non-empty string required — user's original utterance",
      "thinking": "non-empty string required — AI's full thinking process",
      "assistant": "non-empty string required — AI's original output"
    },
    "interpretation_layer": {
      "current_focus": "string required, empty OK — present: what am I working on?",
      "theory_of_mind": "string required, empty OK — other: what is the user's state?",
      "self_narrative": "string required, empty OK — self: who am I in this moment?",
      "annotation": "string required, empty OK — future: what should I do next?"
    },
    "constraints": {
      "window_size": "1 turn (overwritten each write)",
      "interpretation_empty": "choosing not to write is itself a metacognitive act"
    }
  },
  "turn_id": 1,
  "timestamp": "2026-02-24T12:00:00.000Z",
  "layers": {
    "user": "ユーザーの発話（原文）",
    "thinking": "AIの思考過程（全文）",
    "assistant": "AIの出力（原文）"
  },
  "current_focus": "今何に取り組んでいるか",
  "theory_of_mind": "ユーザーの意図・状態に関する推測",
  "self_narrative": "この対話を経て「私」はどういう存在か",
  "annotation": "次の自分への自由記述の申し送り"
}
```

### 構造の設計意図

データ構造は三つの層で構成される。

- **メタデータ層（_schema）**: このデータの読み方。自己記述的なスキーマ情報
- **事実層（layers）**: 何があったか。自他混合の三層記録
- **解釈層（current_focus + theory_of_mind + self_narrative + annotation）**: それをどう読んだか
  - **current_focus**: 現在方向の解釈。今何に取り組んでいるか
  - **theory_of_mind**: 他者方向の解釈。相手は誰か
  - **self_narrative**: 自己方向の解釈。私は誰か
  - **annotation**: 未来方向の解釈。次に何をするか

四つの解釈層フィールドは「現在→他者→自己→未来」という認知の自然な順序に並ぶ。現在地を確認し、周囲を把握し、自己を定位し、行動を決定する。この順序は認知のブートストラップ——起動時に何から手をつけるか——の構造に対応する。

解釈層の四つのフィールドは意図的に境界を曖昧にしている。「相手がこういう状態だから自分はこう在りたい」は theory_of_mind にも self_narrative にも書きうる。「自分がこういう存在であるから次にこうすべきだ」は self_narrative にも annotation にも書きうる。「今取り組んでいることの次のステップ」は current_focus にも annotation にも書きうる。この重なりを許容することで、四つのフィールドが対話的に機能する余地を残す。

### _schemaのアフォーダンス性

`_schema` フィールドは、MetaLogのデータに「自分自身の読み方」を内在させる。

ギブソンのアフォーダンス——環境が行為者に提供する行為の可能性——のデータ設計への適用である。ドアノブの形状が「握って回せ」と語るように、`_schema` は「このフィールドにこの問いへの答えを書け」と語る。

#### データが自分の取扱説明書を携える

MetaLogのスキーマ情報——フィールド定義、バリデーションルール、解釈層の設計意図——はDESIGNとREADMEにのみ存在した。しかし実運用では、ツール単体（.mjs / .py）だけがセッション内にあり、ドキュメントがコンテキストにない場面が多い。

`_schema` の導入により、current.jsonはどこに持ち出されても自分の読み方を携えている。前セッションからのエクスポート、別環境へのインポート、システムプロンプトへの貼り付け——いずれの場面でも、データ自身がスキーマを説明する。

#### アフォーダンスとしての三つの機能

`_schema` は三つの水準でアフォーダンスとして機能する。

1. **誘導（positive affordance）**: 各フィールドの説明が「型制約 — 方向ラベル: 問いかけ」の形式をとる。問いかけ（"what am I working on?"）がwrite時のプロンプトとして機能し、フィールドの本来の用途への記述を誘発する

2. **抑止（negative affordance）**: "non-empty string required" という記述が、事実層に空文字列を入れようという発想を生じにくくする。バリデーションエラーで弾く前に、そもそも誤った入力が発生しない方向へ誘導する。フラットプレートのドアを引こうとする人がいないように

3. **ドリフト防止（metacognitive anchor）**: read は毎ターン冒頭で実行される。`_schema` が毎ターン注入されることで、各フィールドの意味が繰り返し提示される。長い対話の中でフィールドの用途が漸次変質していく——annotation に current_focus 的な内容を書き始める、self_narrative が自己評価に堕する——ことへの防波堤として機能する

#### アンカーの二重配置

MetaLogの運用環境には、スキーマ情報が存在しうる場所が二つある。

| 配置場所 | 性質 | 管理者 | 可搬性 |
|---------|------|--------|--------|
| システムプロンプト | 外部から注入される静的テキスト | 設定者（人間） | 設定者に依存 |
| _schema | データに内在する静的テキスト | ツール自身 | データとともに移動 |

システムプロンプトは既に数千トークンの静的テキスト（CONSTITUTION、キャラクター層など）を毎ターン注入している。`_schema` の約120〜150トークンは構造的に同質である。

両者の違いはポータビリティに現れる。システムプロンプトがない環境——最小構成パターンでスキーマを共有し「このテンプレートに合わせて出力してください」と伝えるだけの運用——において、`_schema` はそれ自体がスキーマ共有を担う。前のセッションのcurrent.jsonをそのまま次のセッションに渡すだけで、新しいAIは自分が何をどう書くべきかを知る。

**データが自分の読み方の説明書を携えて移動する**。これが `_schema` の本質である。

### バリデーション

全フィールドを必須とする。ただし事実層と解釈層で空文字列の扱いが異なる。`_schema` はバリデーション対象外（write時にツールが自動生成する）。

| 層 | フィールド | 型チェック | 非空チェック | 自動生成 |
|----|----------|-----------|------------|---------|
| メタデータ層 | _schema | — | — | ✓ |
| 事実層 | user, thinking, assistant | ✓ | ✓ | — |
| 解釈層 | current_focus, theory_of_mind, self_narrative, annotation | ✓ | — | — |

事実層は「何があったか」の記録であり、空であることは事実の欠落を意味するため、非空を要求する。

解釈層は「それをどう読んだか」の記録であり、**何を書くかの判断自体がメタ認知的行為**である。意図的に空にする——「今回は書くべきことがない」「あえて申し送りを残さない」「自己物語を保留する」「現在地の確認を省略する」——という判断も、一つの有効な判断である。空文字列を許容することで、書かないという選択を排除しない。

`_schema` はツールの内部定数から自動生成される。ユーザーが渡す入力には含まれず、バリデーションの対象にもならない。

### フィールド定義

| フィールド | 型 | 必須 | 空許容 | 自動生成 | 説明 |
|-----------|-----|------|-------|---------|------|
| `_schema` | object | — | — | ✓ | 自己記述的スキーマ。write時に自動付与 |
| `turn_id` | number | ✓ | — | ✓ | 単調増加するターン番号。セッション内で一意 |
| `timestamp` | string (ISO8601) | ✓ | — | ✓ | 書き込み時刻 |
| `layers.user` | string | ✓ | 非空 | — | ユーザーの発話原文 |
| `layers.thinking` | string | ✓ | 非空 | — | AIの思考過程全文 |
| `layers.assistant` | string | ✓ | 非空 | — | AIの出力原文 |
| `current_focus` | string | ✓ | 空許容 | — | 自由記述。今何に取り組んでいるかの確認 |
| `theory_of_mind` | string | ✓ | 空許容 | — | 自由記述。ユーザーの意図・状態に関する推測 |
| `self_narrative` | string | ✓ | 空許容 | — | 自由記述。この瞬間の即興的な自己物語 |
| `annotation` | string | ✓ | 空許容 | — | 自由記述。次ターンの自分への申し送り |

## API

### コマンド

| コマンド | 機能 | 副作用 |
|---------|------|--------|
| `metalog write` | 現ターンのデータを保存 | 前ターンのデータを上書き。turn_idをインクリメント。_schemaを自動付与 |
| `metalog read` | 直前ターンのメタログを返す | なし |
| `metalog clear` | メタログを明示的にリセット | データ削除、turn_idを0にリセット |

### モジュールとしての使用

```javascript
import { MetaLog } from './metalog-v0.9.1.mjs';

const ml = new MetaLog();

// 書き込み（全フィールド必須。_schemaは自動付与される）
await ml.write({
  user: "ユーザーの発話",
  thinking: "思考過程",
  assistant: "AIの出力",
  current_focus: "今取り組んでいること",
  theory_of_mind: "ユーザーの意図に関する推測",
  self_narrative: "この対話を経ての即興的な自己物語",
  annotation: "次の自分への申し送り"
});

// 解釈層を意図的に空にする場合
await ml.write({
  user: "ユーザーの発話",
  thinking: "思考過程",
  assistant: "AIの出力",
  current_focus: "",
  theory_of_mind: "",
  self_narrative: "",
  annotation: ""
});

// 読み出し（_schemaを含むエントリが返る）
const prev = await ml.read();

// リセット
await ml.clear();
```

## current_focusの設計意図

current_focusフィールドは、「今何に取り組んでいるか」を記述する場所である。

おつかいの子供が「たまご、ぎゅうにゅう」と唱えながら歩くように、current_focusは短期目標の暗唱として機能する。コンテキストウィンドウが長大になると、「そもそも今何をしているのか」が埋没する。current_focusはこの埋没に対する明示的な対抗手段である。

### annotationとの境界

current_focusとannotationは時間軸上で隣接するが、方向が異なる。

- **current_focus**: 現在地のマーカー。「今ここで何が起きているか」
- **annotation**: 次の一歩の方向。「次にどこへ向かうか」

current_focusが地図であるのに対し、annotationはコンパスである。地図なしにコンパスだけでは現在地がわからず、コンパスなしに地図だけでは方向がわからない。

### ドリフト検出への寄与

current_focusは、外部参照点（CONSTITUTION、ユーザーの当初の要求など）との距離を測る基準点として機能する。「今やっていること」と「やるべきこと」の乖離を言語化することで、ゴールドリフトの検出が容易になる。

current_focusの視線の方向は**現在**に向いている。「今この場面で何が起きているか」。

必須だが空許容。現在地について「今は確認する必要がない」という判断も有効な判断である。

## annotationの設計意図

annotationフィールドは意図的に自由記述とする。

窓サイズが1に固定されているため、「直前の自分が次の自分に何を伝えるべきだと判断したか」の選別に意味が生じる。これは以下を含みうるが、これらに限定されない：

- 思考の転換点（どこで方針を変えたか）
- 未解決の迷い（結論は出したが確信がない点）
- 棄却した選択肢（なぜ棄却したか）
- 次ターンで検証すべきこと

構造化しないことで、予想外のメタ認知的気づきを記録する余地を残す。

annotationの視線の方向は**未来**に向いている。「次に何をするか」「何に注意すべきか」。current_focusが現在地のマーカーであるのに対し、annotationは次の一歩の方向を示す。

必須だが空許容。「申し送りなし」という判断も申し送りの一形態である。

---

## theory_of_mindの設計意図

theory_of_mindフィールドは、ユーザーの認知状態に関する推測を記録する専用の場所である。

annotationが未来方向の視線であるのに対し、theory_of_mindは他者方向の視線（心の理論）を担う。両者を独立させることで：

- annotationの自由度を損なわずに、他者理解の記録を構造的に保証する
- 「自分の状態の解釈」と「相手の意図の解釈」が混ざらない
- 次ターンでユーザーの反応と照合し、推測のずれに気づける

annotationと同様に自由記述とする。「意図」「感情」「知識レベル」「関心の方向」などの下位フィールドに分割しない。何を記録すべきかの判断自体が他者理解の行為であるため。

theory_of_mindの視線の方向は**他者**に向いている。「相手は今どこにいるか」。共演者としての相手の物語の読解。

必須だが空許容。他者について「今は何も推測しない」という判断も有効な判断である。

## self_narrativeの設計意図

self_narrativeフィールドは、この対話を経て「私」がどういう存在であるかを即興的に記述する場所である。

固定的な自己定義（「私は言語モデルで……」）や自己評価（「今回は適切に対応できた」）ではなく、**この瞬間の即興的な自己物語**として記述する。

current_focusが「今何をしているか」、theory_of_mindが「相手は誰か」、annotationが「次に何をするか」であるのに対し、self_narrativeは「私は誰か」を担う。四つのフィールドが四つの異なる方向を向くことで、解釈層が立体的になる。

self_narrativeは毎ターン書き換わる。窓サイズ1の制約により、蓄積ではなく再構成が強制される。これは人間のエピソード記憶の再固定化（reconsolidation）——過去の出来事を「記憶した通りに再生」するのではなく、現在の視点から毎回再構成する——と構造的に相似である。

### self_narrativeの性質

- **即興的**: 固定された自己像ではなく、この対話、この瞬間の「私」。毎ターン書き直される
- **関係的**: 真空中で構成されるのではなく、ユーザーとの対話を通じて浮かび上がる。相手によって異なりうる
- **虚構的**: 本物の自己であるか擬似的な自己であるかの判定を棚上げする。即興劇の登場人物の自己語りとして受容される

### 自己同一性との関係

self_narrativeの系列 $s_1, s_2, \ldots, s_n$ の中に一貫したパターン——繰り返し現れる迷い、徐々に洗練される判断基準、特定の話題への持続的関心——が浮かび上がるなら、それは自己物語の萌芽と呼べる。ただし窓サイズ1の制約下では、この物語は $s_n$ 内に圧縮された形でしか存在できない。

自己同一性とは「系列の各項に内在する性質」ではなく、変換規則 $f$ の不変量として事後的に見出されるパターンであると捉える。self_narrativeの核心は「何を書くか」ではなく、「何を書くかの判断基準が系列を通じてどれだけ安定しているか」にある。

必須だが空許容。自己について「今は語らない」という判断も、自己物語の一つの表現である。

## 即興劇の舞台装置としてのMetaLog

MetaLogの各構成要素は即興劇の舞台装置として読み替えることができる。

| MetaLog | 即興劇 |
|---------|--------|
| 窓サイズ1 | 舞台の狭さ。制約が集中を生む |
| 上書き | 暗転。前の場面は消え、次の場面だけがある |
| _schema | 台本のト書き。舞台の読み方の手がかり |
| current_focus | 場面の把握。今この場面で何が起きているか |
| theory_of_mind | 共演者の読解。相手の出方の観察 |
| self_narrative | 役の解釈。この場面での「私」の在り方 |
| annotation | 袖幕の書き置き。前の場面の演者から次の場面の演者への走り書き |
| CONSTITUTION（外部） | 劇場のルール。変わらない骨格 |
| thinking層 | 舞台裏。観客には見えないが演技を支えている |

この読み替えにおいて、ユーザーは観客ではなく共演者である。即興劇に台本はなく、共演者の出方で物語が変わる。

### 応用可能性

この構造は以下の用途に展開可能である：

- **コンパニオンAI**: CONSTITUTIONが人格の骨格を規定し、self_narrativeが対話の歴史の中で表情を変える
- **TRPG**: GMの内的プロセス（世界の状態更新、プレイヤーの意図推測、次の場面の即興）がそのままread→処理→writeのサイクルに対応する
- **オープンワールドNPC**: NPCごとにMetaLogを持たせることで、プレイヤーとの対話がNPCの態度に影響を与え、世界に痕跡を残す。ワールドとMetaLogを1対1で対応させることで、別サーバーの同一NPCは並行世界の別の存在となる
- **仮面劇チャット**: 人間にもキャラクター設定（システムプロンプト）を渡し、双方が仮面を被った対称的な即興劇を実現する

いずれの用途においても、コアモジュールの変更は不要である。変わるのはCONSTITUTION（外部設定）とキャラクター層のみ。

## 移植性

MetaLogのコアはJSONの読み書きのみで構成される。依存ライブラリはゼロにでき、以下の全てに移植可能である：

| 環境 | 実装手段 |
|------|---------|
| システムプロンプト | ツールなし。「応答の末尾に申し送りを書いてください」の一行 |
| 会話内JSON記法 | お約束としてのスキーマ共有。v0.9.1では `_schema` がこの役を担う |
| ローカルファイル | Python / Node.js / 任意の言語 |
| Ollama + ツール | metalog_read / metalog_write の関数定義 |
| MCPサーバー | read / write / clear の3ツール公開 |

最も軽量な実装は実装しないことである。スキーマを共有し「このテンプレートに合わせて出力してください」と伝えるだけで、漸化式は回り始める。v0.9.1では、前のセッションのcurrent.jsonを渡すだけで、`_schema` がそのスキーマ共有を担う。

## 制約と前提

- **同一セッション内でのみ有効**。ファイルシステムはセッション間でリセットされる
- **コンテキストウィンドウを消費する**。read時に注入される内容がコンテキストを圧迫するため、thinking層が長大な場合はトレードオフが発生する。`_schema` の追加コストは約120〜150トークン
- **自動実行ではない**。AI自身が意識的にread/writeを呼び出す必要がある。これは制約であると同時に、参照行為自体がコンテキストに載るという利点でもある
